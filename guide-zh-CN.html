BSOD Analyzer — 快速分析按鈕说明

选取 .dmp 文件后，侧边栏会出现 8 个快速分析按钮。每个按钮背后都是预设的 kd.exe 命令组合，执行完毕后会自动将原始输出发送给 AI 进行解读。

🧠 完整 Triage + AI 摘要 优先执行

kd 命令

vertarget; .bugcheck; !analyze -v; kb 100; lm t n; !irql; !sysinfo smbios; !cpuinfo

「全套扫描」按钮。一次执行最常用的 8 条命令，涵盖：OS 版本确认、Bugcheck 代码、详细错误分析、Call Stack、已加载模块列表、当前 IRQL、系统硬件信息（SMBIOS）、CPU 详细信息。AI 收到这批数据后，会输出：

  • Bugcheck 代码与名称
  • 一行根因摘要
  • 肇事模块与驱动程序类型
  • 关键证据引用
  • 3–5 条后续建议的 kd 命令
第一次拿到不熟悉的 dump，或时间有限需要快速定性时，优先点这个。它的输出足以应付 80% 的常见问题，并为后续深挖提供方向。

🔍 !analyze -v

kd 命令

.bugcheck; !analyze -v

单独执行 WinDbg 最核心的自动分析命令。.bugcheck 先列出 Bugcheck 代码及四个参数（Arg1–Arg4），!analyze -v 则进行详尽的错误分析：

  • Bugcheck 名称与机制说明
  • 失败的内存地址、PFN
  • Faulting module（名称、版本）
  • Stack trace 摘要
  • Failure Bucket（问题指纹，可用于比对已知 KB）

AI 会解读代码与参数、判断肇事模块是 inbox（Windows 原生）、第三方或已知问题驱动。

当你已知大方向，想精准确认肇事驱动与 Arg 意义时使用。也适合在「完整 Triage」之后，对某个可疑驱动做二次确认。

📚 Call Stack (kb 100)

kd 命令

kb 100; !thread

kb 100 显示崩溃时最多 100 个 stack frame，每个 frame 包含返回地址、函数名称（需符号）和前三个参数。!thread 则输出当前线程的完整信息。AI 会对每个 frame 逐一标注，并：

  • 指出崩溃发生点（最高的有效 frame）
  • 标记 user-mode / kernel 切换点
  • 高亮任何第三方驱动 frame
当 !analyze -v 指向的驱动看起来像「受害者」而非「凶手」，需要回溯 call chain 才能找到真正的调用来源时使用。

💻 已加载模块 (lm t n)

kd 命令

lm t n

列出崩溃时内存中所有已加载的模块，包含基地址、大小、名称、路径与符号状态。AI 会从列表中标记：

  • 第三方驱动（非 Microsoft）
  • 可由日期推测过时或未签名的驱动
  • 已知高风险类别：杀毒软件、VPN、RGB 控制、超频工具
  • 建议用 lmvm <模块名> 进一步查询的项目
系统环境复杂（安装大量第三方软件），或 !analyze -v 指向的模块版本太旧时使用。

🖥️ 系统 / CPU / BIOS

kd 命令

vertarget; !sysinfo smbios; !cpuinfo
命令输出内容
vertargetWindows OS 版本、Build 号、Service Pack、内存大小
!sysinfo smbiosBIOS 版本/日期、主板制造商与型号、系统序号
!cpuinfoCPU 系列、型号、Stepping、Microcode 版本
怀疑是 BIOS bug 或 Microcode 问题、需确认系统基本资料填写 bug report 时使用。

🧮 内存 / Pool

kd 命令

!vm; !poolused 2; !memusage 0
命令输出内容
!vm虚拟内存统计：总可用 VA、已提交、Paged/NonPaged Pool 大小与上限
!poolused 2按 Pool Tag 分类的 NonPaged Pool 用量，依大小降序，用于找泄漏来源
!memusage 0物理内存页面使用摘要（可用、已使用、Transition、Modified 等）
Bugcheck 是 POOL_CORRUPTION / OUT_OF_MEMORY 相关，或怀疑有内存泄漏（跑一段时间后才 BSOD）时使用。

🧵 当前 Thread / IRQL

kd 命令

!thread; !irql; kv
命令输出内容
!thread当前线程的完整信息：TEB、状态、等待链、stack 指针
!irql当前 IRQL，显示发生崩溃时的中断等级
kvVerbose call stack，包含 frame pointer 与 trap/exception frame 标记
Bugcheck 是 IRQL_NOT_LESS_OR_EQUAL，或 !analyze -v 显示 IRQL 为 2（DISPATCH_LEVEL）以上，怀疑 DPC / ISR 有问题时使用。

📄 生成 Markdown 报告

这个按钮不执行任何新的 kd 命令，而是把本次 session 中所有已收集到的 kd 输出一次发给 AI，要求生成一份结构化的 Markdown 分析报告，包含：

  • Bugcheck Summary（表格：代码、名称、说明、Arg1-4、Failure Bucket）
  • Root Cause（单行摘要）
  • System Information（制造商、型号、BIOS、CPU、OS）
  • Faulting Component（模块、符号、驱动类型）
  • Call Stack（逐 frame 标注）
  • Evidence（引用原始 kd 输出片段）
  • Recommendations（驱动版本、KB 号、BIOS URL、registry 设置）
  • Confidence & Residual Uncertainty

缺少的字段会填入「N/A」，AI 不会凭空捏造数值。报告同时会自动保存为 .md 文件，并在文件资源管理器中打开所在文件夹。

⚠️ 若 session 中完全没有执行过任何其他按钮，会出现提示要求先执行至少一个分析步骤。

📋 建议流程

1. 选取 .dmp ↓ 2. 🧠 完整 Triage + AI 摘要 ← 必做，获得全局概览 ↓ 3. 根据 AI 建议，选择性执行： ├─ 怀疑驱动问题 → 💻 已加载模块 ├─ Call Stack 需深挖 → 📚 Call Stack ├─ 疑似内存泄漏 → 🧮 内存 / Pool ├─ IRQL 相关崩溃 → 🧵 当前 Thread / IRQL └─ 需确认硬件规格 → 🖥️ 系统 / CPU / BIOS ↓ 4. 💬 自由提问（对话框可继续追问） ↓ 5. 📄 生成 Markdown 报告 ← 最后一步，输出正式报告

各按钮的输出会在 session 中累积，后续按钮与自由提问都能引用前面已收集的数据，不需重复执行。
