BSOD Analyzer — 快速分析按鈕說明

選取 .dmp 檔案後，側邊欄會出現 8 個快速分析按鈕。每個按鈕背後都是預設的 kd.exe 指令組合，執行完畢後會自動把原始輸出送給 AI 進行解讀。

🧠 完整 Triage + AI 摘要 優先執行

kd 指令

vertarget; .bugcheck; !analyze -v; kb 100; lm t n; !irql; !sysinfo smbios; !cpuinfo

「全套掃描」按鈕。一次執行最常用的 8 條指令，涵蓋：OS 版本確認、Bugcheck 代碼、詳細錯誤分析、Call Stack、載入模組清單、目前 IRQL、系統硬體資訊（SMBIOS）、CPU 詳細資訊。AI 收到這批資料後，會輸出：

  • Bugcheck 代碼與名稱
  • 一行根因摘要
  • 肇事模組與驅動程式類型
  • 關鍵證據引用
  • 3–5 條後續建議的 kd 指令
第一次拿到不熟悉的 dump，或時間有限需要快速定性時，優先點這個。它的輸出足以應付 80% 的常見問題，並替後續深挖提供方向。

🔍 !analyze -v

kd 指令

.bugcheck; !analyze -v

單獨執行 WinDbg 最核心的自動分析指令。.bugcheck 先列出 Bugcheck 代碼及四個參數（Arg1–Arg4），!analyze -v 則進行詳盡的錯誤分析：

  • Bugcheck 名稱與機制說明
  • 失敗的記憶體位址、PFN
  • Faulting module（名稱、版本）
  • Stack trace 摘要
  • Failure Bucket（問題指紋，可用於比對已知 KB）

AI 會解讀代碼與參數、判斷肇事模組是 inbox（Windows 原生）、第三方或已知問題驅動。

當你已知大方向，想精準確認肇事驅動與 Arg 意義時使用。也適合在「完整 Triage」之後，對某個可疑驅動做二次確認。

📚 Call Stack (kb 100)

kd 指令

kb 100; !thread

kb 100 顯示崩潰當下最多 100 個 stack frame，每個 frame 包含返回地址、函數名稱（需符號）和前三個參數。!thread 則輸出目前執行緒的完整資訊。AI 會對每個 frame 逐一標注，並：

  • 指出崩潰發生點（最高的有效 frame）
  • 標記 user-mode / kernel 切換點
  • 高亮任何第三方驅動 frame
當 !analyze -v 指向的驅動看起來像「受害者」而非「兇手」，需要回溯 call chain 才能找到真正的呼叫來源時使用。

💻 載入模組 (lm t n)

kd 指令

lm t n

列出崩潰當下記憶體中所有已載入的模組，包含基底位址、大小、名稱、路徑與符號狀態。AI 會從清單中標記：

  • 第三方驅動（非 Microsoft）
  • 可由日期推測過時或未簽署的驅動
  • 已知高風險類別：防毒軟體、VPN、RGB 控制、超頻工具
  • 建議用 lmvm <模組名> 進一步查詢的項目
系統環境複雜（安裝大量第三方軟體），或 !analyze -v 指向的模組版本太舊時使用。

🖥️ 系統 / CPU / BIOS

kd 指令

vertarget; !sysinfo smbios; !cpuinfo
指令輸出內容
vertargetWindows OS 版本、Build 號、Service Pack、記憶體大小
!sysinfo smbiosBIOS 版本/日期、主機板製造商與型號、系統序號
!cpuinfoCPU 家族、型號、Stepping、Microcode 版本
懷疑是 BIOS bug 或 Microcode 問題、需確認系統基本資料填寫 bug report 時使用。

🧮 記憶體 / Pool

kd 指令

!vm; !poolused 2; !memusage 0
指令輸出內容
!vm虛擬記憶體統計：總可用 VA、已提交、Paged/NonPaged Pool 大小與上限
!poolused 2按 Pool Tag 分類的 NonPaged Pool 用量，依大小降冪，用於找洩漏來源
!memusage 0實體記憶體頁面使用摘要（可用、已使用、Transition、Modified 等）
Bugcheck 是 POOL_CORRUPTION / OUT_OF_MEMORY 相關，或懷疑有記憶體洩漏（跑一段時間後才 BSOD）時使用。

🧵 目前 Thread / IRQL

kd 指令

!thread; !irql; kv
指令輸出內容
!thread目前執行緒的完整資訊：TEB、狀態、等待鏈、stack 指標
!irql目前 IRQL，顯示發生崩潰時的中斷等級
kvVerbose call stack，包含 frame pointer 與 trap/exception frame 標記
Bugcheck 是 IRQL_NOT_LESS_OR_EQUAL，或 !analyze -v 顯示 IRQL 為 2（DISPATCH_LEVEL）以上，懷疑 DPC / ISR 有問題時使用。

📄 產生 Markdown 報告

這個按鈕不執行任何新的 kd 指令，而是把本次 session 中所有已收集到的 kd 輸出一次餵給 AI，要求產生一份結構化的 Markdown 分析報告，包含：

  • Bugcheck Summary（表格：代碼、名稱、說明、Arg1-4、Failure Bucket）
  • Root Cause（單行摘要）
  • System Information（製造商、型號、BIOS、CPU、OS）
  • Faulting Component（模組、符號、驅動類型）
  • Call Stack（逐 frame 標注）
  • Evidence（引用原始 kd 輸出片段）
  • Recommendations（驅動版本、KB 號、BIOS URL、registry 設定）
  • Confidence & Residual Uncertainty

缺少的欄位會填入「N/A」，AI 不會憑空捏造數值。報告同時會自動儲存為 .md 檔案，並在檔案總管中開啟所在資料夾。

⚠️ 若 session 中完全沒有執行過任何其他按鈕，會出現提示要求先執行至少一個分析步驟。

📋 建議流程

1. 選取 .dmp ↓ 2. 🧠 完整 Triage + AI 摘要 ← 必做，得到全局概覽 ↓ 3. 根據 AI 建議，選擇性執行： ├─ 懷疑驅動問題 → 💻 載入模組 ├─ Call Stack 需深挖 → 📚 Call Stack ├─ 疑似記憶體洩漏 → 🧮 記憶體 / Pool ├─ IRQL 相關崩潰 → 🧵 目前 Thread / IRQL └─ 需確認硬體規格 → 🖥️ 系統 / CPU / BIOS ↓ 4. 💬 自由提問（對話框可繼續追問） ↓ 5. 📄 產生 Markdown 報告 ← 最後一步，輸出正式報告

各按鈕的輸出會在 session 中累積，後續按鈕與自由提問都能引用前面已收集的資料，不需重複執行。
